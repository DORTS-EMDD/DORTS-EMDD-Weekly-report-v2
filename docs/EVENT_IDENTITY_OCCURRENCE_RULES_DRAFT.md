**核心結論：**
- 在多語自由文字中，「是否同一 occurrence」需要語意閱讀，現有元件中只有 helper 能做。
- 能做到確定性的，是：資格判定、地區、相同頁面、請求建構、提案驗證、兩階段同意、分組、揭露與重放。
- 語意部分的正確作法是：
  - 定義清楚；
  - 要求兩次獨立同意（提案＋確認）；
  - 全部記錄、可重放；
  - 以標註語料量測。
- 而不是把它包裝成「事實」。

## 1. 七項規則

### R1　關係模型與 DISTINCT 權威（D1）

**規則文字**
1. EventIdentity 對每一配對只作三種判定：
   - `SAME_EVENT`
   - `DISTINCT_EVENT`
   - `UNCERTAIN`（證據不足）
2. `DISTINCT_EVENT` 只能來自上游 owner 已確立、並由 Python 以確定性規則比較的事實。
   - 現行唯一一項：兩者的 EvidenceService 地區皆已確立且不同（RC-22）。
   - 行為不變，改以 `DISTINCT_EVENT`（basis `REGION`）記錄。
3. Event Identity 內的任何 helper 輸出——提案分群、確認、或任何 occurrence 屬性——都不得產生 `DISTINCT_EVENT`，也不得被記錄成 Python 判定的事實。
4. 新增任何 DISTINCT 依據，必須是確定性、可重現的事實，並另經使用者核准。
5. helper 沒有把兩筆放在同群，只代表 `UNCERTAIN`。
6. `UNCERTAIN`：
   - 不合併，下游不得救回；
   - 不是技術缺口；只有起因是技術失敗時，依 RC-6 照舊揭露。

**說明**
- 地區的來源值，是 EvidenceService 經 metadata 擷取（helper 引用原文）取得，再以參照表確定性解析。
- 它是上游 owner 的權威判定（RC-4、RC-22，已核准），Event Identity 不重判。
- 這與 v1 的 occurrence type 不同：type 是 Event Identity 自己的 helper 輸出。

**Owner**：EventIdentity。

**關係影響**：唯一的 DISTINCT 來源；其餘未確立 SAME 者，一律為 UNCERTAIN。

**案例**：仁川、光州、大邱都在韓國，彼此不會因地區分開；林茲（AT）與德勒斯登（DE）因地區分開。

**ED01–ED26**：不變。

**風險**
- Under-merge：上游地區判錯時發生，與今日相同。
- Over-merge：本條不會造成。

### R2　判定順序與 exact-source 條件（D1）

**規則文字**（每一配對依序判定）
1. 地區 DISTINCT 成立 → `DISTINCT_EVENT`。
2. exact-source → `SAME_EVENT`，須同時符合：
   - 正規化後的 canonical URL 相同；
   - substantive content 相同且非空；
   - 兩筆的 Scope 候選事件焦點相同（焦點句集合相同；兩筆都沒有焦點也視為相同）。

   不符合時，進入下一步。
3. exact-fact path → `SAME_EVENT`（不變；production 從未觸發）。
4. helper path（R6）→ `SAME_EVENT`。
5. 其餘 → `UNCERTAIN`。

complete-link 分組不變：一筆紀錄同時可併入兩個互不相容的群時，併入排序最前的群，並記錄 `INSUFFICIENT_IDENTITY`。

**理由**
- 同一頁面可同時報導多個事件（綜合整理、直播頁、狀態頁）。
- Scope 逐筆決定候選事件；焦點不同，就是不同的候選事件，應交由 helper 比對，不能因頁面相同而直接合併。
- 焦點比對是確定性的。

**殘餘風險**
- 狀況：同一頁面、同一內容、同一焦點，卻是兩次不同的 occurrence。例如同一段文字被重複用於兩天的通告。
- 這時兩筆的 Evidence 完全相同，無法區分；要區分只能靠刊登時間，而 RC-38 禁止以刊登時間判定。
- 因此視為同一事件，並記錄為殘餘風險。
- 另一個選擇是改判 UNCERTAIN，但報告會出現文字完全相同的兩則。

**實測**：四次 Live（40838021391、40985179898、40999869397、41018554355）中，沒有任何兩筆紀錄共用 canonical URL；exact-source 從未觸發，本條件不影響過去結果。

**Owner**：EventIdentity。

**ED01–ED26**：不變。ED01 兩筆都沒有焦點，仍合併。

**風險**
- Over-merge：只剩上述殘餘情況。
- Under-merge：同一頁面因 Scope 呼叫間變動得到不同焦點時，改由 helper 判斷；可能多一則重複。

### R3　Occurrence 的定義與粒度（D2；由 helper 判斷，Python 不執行）

**規則文字**
1. 一個 occurrence，是一個主體所遭遇、或一個行為者所做的一個具體行為或事情，發生在一個時間或一段連續期間。
2. 即使主體相同，下列仍為**不同** occurrence：
   1. 不同階段：招標／決標或簽約／交付／不載客的測試或試運轉／完工或開始供使用（含載客試營運）。
   2. 事故或服務中斷 vs 其調查或稽核結果的公布 vs 事後的決定或措施。
   3. 里程碑 vs 為標示或驗證它而辦的活動（典禮、視察、體驗乘車）。（使用者決定；ED19）
   4. 本身就是新聞的發言、呼籲、質詢或會議 vs 發言所提及的事項。
   5. 同類事件的不同次（不同日、不同地點或不同對象）。
3. 下列為**同一** occurrence：
   1. 不同宣布者或報導者報導的同一事項。（使用者決定；ED26）
   2. 同一交付物的「建置或安裝完成」與「開始供使用」。（ED26）
   3. 某事項排定於某日發生的報導，與其已於該日發生的報導——須 Evidence 確認為同一主體的同一排定行為。**【新增，需確認】**
   4. 非識別細節缺漏或寫法不同（§K；提示詞 v8）。
4. 一筆紀錄的事件，是它的 Scope 候選事件。焦點同時報導兩個 occurrence 時：
   - 該紀錄只能與其中一個 occurrence 的紀錄同群，且須有相符的具體細節；
   - 無法判定歸屬時，單獨成群（UNCERTAIN）。**【澄清，需確認】**

**Owner**：EventIdentity。由 helper 在提案與確認中適用；Python 不執行本條任何部分。

**關係影響**：只透過 helper path 影響 SAME；違反本條的 helper 回答不會被 Python 擋下（見 §3）。

**案例預期**
- **仁川：**
  - 開通報導（8／10 筆，含議員宣布「完成建置」）為一個 occurrence（3.1、3.2）。
  - 部會體驗活動為另一個（2.3）。
  - 國會發言為另一個（2.4）。
  - 混合焦點的 `a071ba69`、`9ce03b4d` 寫有「運延站～仁川市廳站」「體驗行事」等細節，依 4 歸入體驗活動。
- **光州：**
  - 2 號線稽核的兩篇報導為同一 occurrence（同一稽核委員會、同一建設本部綜合稽核、相同發現）。
  - 同週的「2 號線站名確定」是不同 occurrence（決定，2.1／2.2）。
- **大邱：**
  - 火災聯合演練 7 筆為一個 occurrence（20 日起的同一系列）。
  - 明德站新出入口 30 日開通的 2 筆為一個 occurrence。
  - 說明文字中區長的開通前檢查，是另一個活動（2.3）。

**ED01–ED26**：不變。Golden 以腳本代替 helper 回答，提示詞內容不影響其結果。

**風險**
- helper 誤用本條時兩種方向都可能發生。
- Over-merge：例如開通與體驗活動被合併。由「提案＋確認」兩次同意防範：在 11 份真實回答中，提案曾錯提 9 組與 2 組不同事件配對，確認回答錯併 0 組。
- Under-merge：今日已實測，同一請求三次提案找到 40／52／58 of 61。

### R4　Occurrence 日期（D3；由 helper 判斷；任何人都不推定日期）

**規則文字**
1. 只有描述 occurrence 本身時間的日期才算：
   - 一次性的行為或事情：發生日。
   - 跨日事件：起日或起訖期間。「某日仍在持續」不是。
   - 預告事件：排定的日期。
   - 決定：作出決定的日期，不是生效日或實施日。
   - 發言或活動：發言、舉行的日期。
   - 某人「宣布」或「表示」某事項的日期，不是該事項本身的日期。
   - 刊登、更新、byline、dateline、報導時間，永不採用（RC-38、ED09）。
2. 任何人（Python 或 helper）都不得以刊登時間、所在國或時區，把相對或不完整的寫法推定為曆日。例如：昨天、週二、本月、「25 日」。
3. 一個日期寫法只提供它明寫的欄位（年、月、日）。以相對方式表達的欄位（本月、去年、週二）視為未寫。
4. 兩個 occurrence 日期，只在雙方都明寫的欄位上比較；任一欄位不同，即為不一致。只有一方寫出的欄位，不比較。
   - 「25 日」vs「10 月 25 日」：一致。
   - 「12 月 30 日」vs「2026 年 12 月 30 日」：一致。
   - 「25 日」vs「26 日」：不一致。
   - 「週二晚間」vs「10 月 21 日」：不比較。
5. 不一致時適用 RC-38（不變）：
   - 只有其他 Evidence 確認是同一行為者的同一具體行為，才可為 SAME；
   - 可能是同類不同次者，維持分開；
   - helper 不得自選某一來源的日期作為正確。
6. 日期一致或不比較時，日期不影響判斷。

**為何可泛化**
- 不使用任何時區、刊登時間或月曆推算，所以跨國、月底、年底都不會被錯誤推定。
- 時區造成的一天之差（同一時刻在兩地是不同日），屬於「不一致」，由 RC-38 要求其他具體細節確認；日期本身不會造成合併，也不會造成分開。

**Owner**：EventIdentity。由 helper 適用；Python 不解析日期（exact-fact path 的 `occurrence_date` 規則不變）。

**案例預期**
- **仁川：** 開通「21일부터」與未寫日期者，不比較；體驗活動 21 日 vs 國會發言 23 日，不一致（且依 R3 2.3、2.4 本就不同）。
- **光州：** 「25일」vs「26일」不一致，依 RC-38 由相同具體細節確認為同一事件（同 ED21）。
- **大邱：** 「지난 20일」「어제(20일)」「10월 20일(화)」「20일부터」的日欄位都是 20，一致；「21일 밝혔다」是發言日，不是演練的日期。

**ED01–ED26**：不變。ED06、ED09、ED20 走 exact-fact path，不受影響；ED21 仍以相同細節合併。

**風險**
- Under-merge：「週二」對「10 月 27 日」這類無法比較的寫法，日期無法協助判斷，只能依其他細節。
- Over-merge：不會比 RC-38 更寬鬆。

### R5　主體識別，含跨語言（D4；由 helper 判斷）

**規則文字**
1. 主體是具體實體：路線或系統、車輛或車隊、設施（車站、出入口、機廠）、專案或合約標包；決定、活動、發言類另含行為者（機關或個人）。
2. 可以作為同一主體的依據：
   - 同一名稱的翻譯、音譯、羅馬拼音、文字變體；
   - 紀錄自身展開的簡稱或描述；
   - 兩筆都陳述且相符的具體細節：數量、具名地點、當事人、時間。
3. 不可以作為依據：
   - Evidence 以外的知識（誰營運哪條線、某線位於哪個城市）；
   - 相同的城市、國家、系統、主題或專案；
   - 標題、出版者、URL、刊登時間；
   - 用另一筆紀錄的內容，補足本筆沒寫的事。
4. 一筆只以通稱指稱主體（「地下鐵」、未寫城市的「2 號線」），且沒有相符的具體細節時，判為 UNCERTAIN。
5. Python 不比較名稱、別名、拼寫或地點；country、`transit_system_name`、location 仍是 formal-only（§K 不變）。

**Owner**：EventIdentity。由 helper 適用；第 5 點由 Python 遵守。

**案例預期**
- **仁川：**
  - 「인천지하철 1·2호선」＝「仁川地下鉄1・2号線」（翻譯）。
  - 「358량」「운연역~인천시청역」可作為相符細節。
- **光州：** 「광주도시철도 2호선」與「도시철도건설본부 종합감사」相符。
- **大邱：** 「두류역」「11월 27일까지」可作為相符細節。

**ED01–ED26**：不變（ED08 的多語合併以腳本回答）。

**風險**
- Over-merge：同國不同城市的同類事件。由第 3、4 點與確認防範；今日的提示詞已有「不同城市是不同事件」。
- Under-merge：寫法籠統的報導。

### R7　驗證、量測與 Golden 分類（治理）

**規則文字**
1. **Golden 只鎖兩類結果：**
   - A：記錄的領域事實。腳本中的 helper 回答須是正確答案；或者是機制必須克服的 helper 缺陷，例如 ED17、ED24，其預期仍是領域事實。
   - B：與領域事實不衝突的契約不變式。例如：complete-link、輸入順序不影響結果、無效回答揭露缺口、上游資格。
2. **預期結果與記錄本身的領域事實相反的案例（C）屬機制回歸測試，不放在 Golden。** C 是指腳本化一個 helper 缺陷、且機制以 fail-closed 回應的案例。
3. **R3–R5 只能以真實回答語料驗證**（`acceptance/event_identity/recorded_answers.json`，加上人工標註）。
   - 每次修改 Event Identity 提示詞，合併前須在語料上重量測。付費呼叫須另行核准並設上限。
   - 必要條件：已標註為不同事件的配對，經確認後被合併的數量 = 0。
   - 召回率與基準並列報告。
4. **每次 Live 都記錄 helper 往返**（RC-46）。
   - Live 出現的重複或誤合併，加入語料並標註。
   - 只有能化為「領域事實＋正確回答」的案例，才進 Golden。
5. **不得宣稱 Live 不會再有重複或誤合併。** 品質陳述只依記錄的量測。

**Owner**：EventIdentity（測試與驗收）；不參與任何 production 判定。

## 3. 確定性 vs 依賴 helper

**確定性（Python；依記錄的輸入可完全重現）**
- 上游資格檢查。
- 地區 DISTINCT。輸入是 EvidenceService 的權威地區。
- exact-source（含焦點條件）。
- exact-fact path。
- 請求建構：排序、編號、大小上限、分批、反序第二次提案。
- 提案驗證：schema、紀錄代號、句子引用、逐成員淘汰。
- 確認要求與判定最終性。
- complete-link 分組與排序取捨。
- 技術缺口揭露。
- 往返記錄與完全重放（RC-46）。

**依賴 helper（每次呼叫可能不同；由兩次同意、記錄、語料量測約束）**
- 兩筆紀錄是否同一 occurrence，即 R3 粒度、R4 日期解讀、R5 主體。

**上游 owner 的 helper 判定（Event Identity 視為權威輸入，不重判）**
- Scope 的候選事件焦點。
- EvidenceService 地區的來源值。

**無法確定性化（現有元件下）**
- occurrence 種類、日期歸屬（哪個日期屬於哪個行為）、跨語言主體同一性。
- 三者都需要語意閱讀多語自由文字；任何 Python「事實」都只是記錄下來的 helper 輸出（v1 的錯誤）。

## 5. 需要使用者明確確認的新增或變更

1. **R1：** Event Identity 內的 helper 輸出不得產生 DISTINCT；地區（RC-22）是唯一的 DISTINCT 依據。
2. **R2：** 地區 DISTINCT 先於 exact-source；exact-source 增加焦點相同的條件；殘餘情況視為同一事件。
3. **R3 3.3【新增】：** 預告與實際發生，在 Evidence 確認為同一排定行為時，為同一 occurrence。
4. **R3 4【澄清】：** 混合焦點的紀錄只能歸入一個 occurrence；無法判定歸屬時單獨成群。
5. **R4：** 不推定日期；欄位比較規則。
6. **R6 6：** RC-44 的撤回條件改為「須有仍使 ED24 為 [3] 的替代」。
7. **R7：** Golden 分類原則；ED22、ED23、ED25 移為回歸測試。
